## Investigation findings (verified against actual code, NOT the bug-report guesses)

The bug report listed several "likely causes" — only ONE of them is actually true (insufficient outer padding). The dominant cause is something the bug report did not mention: image overflow inside the tile. Both must be fixed.

### Cause 1 — primary: CoverImage uses `.scaledToFill()` without a constraining frame BEFORE blur

In `ProgressGalleryView.swift` lines 155–181, `CoverImage` renders a UIImage like this:

```swift
private struct CoverImage: View {
    let relativePath: String
    @State private var image: UIImage?
    var body: some View {
        Group {
            if let img = image {
                Image(uiImage: img)
                    .resizable()
                    .scaledToFill()        // ← image extends beyond parent bounds
            } else {
                Rectangle()
                    .fill(Color(uiColor: .secondarySystemBackground))
            }
        }
        .task(id: relativePath) { ... }
    }
}
```

Then in `GalleryTileView` (lines 92–126):

```swift
ZStack(alignment: .bottom) {
    CoverImage(relativePath: tile.coverRelativePath)
        .blur(radius: 24, opaque: true)         // ← blur on UNCLIPPED, oversized image
        .clipShape(RoundedRectangle(cornerRadius: 14))  // shape clip, NOT layout clip
    VStack { /* date label, stats, etc. */ }
        .frame(maxWidth: .infinity, alignment: .leading)
}
.aspectRatio(1, contentMode: .fit)  // ← applied at ZStack level
```

`.scaledToFill()` on an `Image` does NOT constrain the image to its parent's frame — it scales the image so the smaller dimension matches the available space, and the image then visually extends past the frame on the other axis. SwiftUI uses the image's natural size when reporting layout to the parent ZStack. Combined with `.blur(opaque: true)` (which renders at the source size, not clipped) the ZStack's intrinsic size becomes the oversized image's size — and `.aspectRatio(1, contentMode: .fit)` then fits THAT to a square, but the underlying ZStack content has already expanded its bounding box. `.clipShape` only masks the visible pixels for rounded corners — it does NOT constrain layout.

Net effect: in a 2-column LazyVGrid with `.flexible()`, the layout system reserves a column-sized slot, but the tile content draws beyond that slot (negative leading offset visually) because the image and its blur weren't clipped to the column width before aspectRatio collapsed the ZStack to a square. The result the user sees: a tile that overflows to the left of column 1.

### Cause 2 — contributing: outer padding (12pt) is below the 16pt convention used elsewhere in Overview

`ProgressGalleryView.swift` line 44: `.padding(12)` on the LazyVGrid.

Convention check (verified):

- `iosApp/iosApp/Views/Overview/OverviewView.swift` line 70: `.padding(.horizontal, 16)` on the outer VStack inside ScrollView.
- `iosApp/iosApp/Views/Overview/OverviewView.swift` line 459 (NutritionGoalsBannerView): `.padding(.horizontal, 16)`.
- The Overview header card / banner / sections all sit at 16pt from the screen edge.

12pt vs 16pt is small but it pushes the gallery 4pt closer to the screen edge than every adjacent surface — and combined with Cause 1, the leading character of the date label ends up under or against the safe-area edge.

to:

```swift
var body: some View {
    Group {
        if let img = image {
            Image(uiImage: img)
                .resizable()
                .scaledToFill()
        } else {
            Rectangle()
                .fill(Color(uiColor: .secondarySystemBackground))
        }
    }
    .frame(maxWidth: .infinity, maxHeight: .infinity)
    .clipped()
    .task(id: relativePath) {
        self.image = await Self.loadOffMain(relativePath: relativePath)
    }
}
```

The added `.frame(maxWidth: .infinity, maxHeight: .infinity)` makes the CoverImage report a flexible size to its parent (so it adopts the column-derived width that LazyVGrid gives it), and `.clipped()` clips overflow at the layout level (NOT just visually), so the oversized `.scaledToFill()` image cannot leak past the tile's bounds when `.blur(opaque: true)` is applied on the parent.

**Why before .blur, not after:** `.blur(opaque: true)` and the rounded `.clipShape` are both applied on `CoverImage` at the call site (lines 95–96 in `GalleryTileView`). The clip needs to happen INSIDE `CoverImage` so the layout system sees a constrained size for the unblurred image before blur expands its render bounds. Adding `.clipped()` on the call site (after `.blur`) does NOT fix the root cause — by then the layout system has already used the oversized intrinsic size for grid sizing.
