<risks_pitfalls>
- **Helper-Func-Sichtbarkeit:** `private fun parsePerSetReps(...)` in WorkoutTemplate.kt kann private sein. Nach dem Move ins Mapper-File bleibt es `private` (file-private = mappers/WorkoutTemplateMappers.kt-private). Sollte funktionieren. Falls die Funktion `internal` oder `public` ist und von anderem domain-Code referenziert wird → bleibt in domain/model und der Mapper importiert sie.
- **Companion-Object-Methods auf Exercise:** Wenn `Exercise.kt` companion methods wie `Exercise.fromEntity(...)` (statt extension `Entity.toDomain()`) hätte, wäre die Migration komplexer. Schaue vorher genau hin. Falls so → in den Mapper als Top-Level-Function `fun toExercise(entity: ExerciseEntity): Exercise`.
- **`@OptIn(kotlin.uuid.ExperimentalUuidApi::class)`** o.ä. File-Level-Annotations: müssen mit dem Mapper-File mitgenommen werden, falls für UUID-Generierung relevant.
- **kotlinx-serialization-JSON-Parser:** Wenn `Exercise.toDomain()` heute `Json.decodeFromString` nutzt, braucht der neue Mapper-File den entsprechenden Import. Status-quo läuft mit `try { ... } catch (Exception)` (siehe CONCERNS Smell 5 / Fragile Areas) — Verhalten 1:1 mitnehmen.
- **iOS-Swift-Interop:** Domain-Models werden vermutlich an Swift exposed (z.B. `Shared.Exercise` als VM-Property). Extension-Functions sind Swift-unsichtbar. Move ändert Swift-API NICHT.
- **Atomic commit:** Ein commit; zwei Aggregate gleichzeitig.
</risks_pitfalls>
