# Plan 20-07: AI-UseCases entkoppeln via AiClient-Port + OpenFoodFacts-Adapter (Smell 4)

<objective>
Smell 4: Domain/Ai/Use-Cases (`WorkoutAiUseCase`, `RecipeAiUseCase`, `SearchFoodsRemoteUseCase`) hängen heute direkt an `data.api.OpenAICompatibleClient` + Ktor-DTOs (`ChatMessage`, `ChatRequest`, `JsonSchemaSpec`, `WorkoutAiResponse`, …) bzw. `data.api.OpenFoodFactsApi`. Sie werden umgestellt auf:
- `AiClient` (Port, Plan 20-01) ↔ `OpenAiCompatibleAiClient` (Adapter, neu in `infrastructure/ai/`)
- `RemoteFoodSearchClient` (Port, neu in `domain/nutrition/`) ↔ `OpenFoodFactsAdapter` (Adapter, neu in `infrastructure/nutrition/`)

DTO-Mapping (Ktor `WorkoutAiResponse` → Domain `WorkoutAiPreview`, `RecipeAiResponse` → `RecipeAiPreview`, OFF-DTO → `Food`) wandert komplett in den Adapter.

Use-Case-Signaturen geben künftig nur Domain-Typen zurück — die Use-Cases werden Ktor-frei.

Purpose: Klares Domain-↔-Infrastructure-Cut für die AI-Vertikale, ohne Schema-/Verhaltens-Änderungen. Bisheriges Fallback-Verhalten (`json_schema` → `json_object`, AiError-Mapping, Streaming-Progress-Callback) bleibt vollständig erhalten — wird nur in den Adapter verschoben.

Output: Plan-20-01-Port wird wirklich genutzt; ein neuer Adapter pro Smell-4-Subsystem; Use-Cases haben keine `data.api.*`-Imports mehr.
</objective>
